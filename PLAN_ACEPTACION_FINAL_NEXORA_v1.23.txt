IMPACTO NEXORA v1.23.0
PLAN DE ACEPTACION FINAL, STAGING Y RESTORE DRILL
=================================================

OBJETIVO
--------
Validar Nexora sin poner en riesgo la base productiva.

A. AMBIENTE DE PRUEBAS SEPARADO
-------------------------------
La aceptación final requiere un ambiente separado de producción.

Recomendación en Railway:
1) Crear un Environment temporal, por ejemplo "staging" o "acceptance".
2) Desplegar el mismo commit aprobado de GitHub.
3) Crear/usar una MySQL de pruebas separada.
4) Nunca reutilizar DATABASE_URL de producción.
5) Usar una SECRET_KEY distinta.
6) No conectar el dominio productivo.
7) Si se prueba restore, el destino debe ser exclusivamente la DB temporal.

El criterio "Ambiente de pruebas separado" se aprueba únicamente después de
comprobar que el DATABASE_URL del ambiente de prueba no corresponde a la base
productiva.

H. RESTORE DRILL REAL
---------------------
1) En producción, crear/descargar un backup reciente.
2) Preparar MySQL temporal de pruebas.
3) Definir en el ambiente de prueba:
   RESTORE_DATABASE_URL=mysql+pymysql://.../BASE_TEMPORAL
4) Mantener DATABASE_URL apuntando a producción solo si la ejecución se realiza
   desde un contexto controlado; preferiblemente ejecutar el script desde
   staging con DATABASE_URL de staging.
5) Ejecutar:
   python -m scripts.restore_backup /ruta/impacto_nexora_....zip
6) El script debe responder:
   Restauración de prueba verificada
   y mostrar table_count > 0.
7) Abrir staging conectado a la DB restaurada y comprobar:
   - login;
   - cliente de muestra;
   - venta de muestra;
   - proyecto/tarea;
   - auditoría.
8) Eliminar o aislar la DB temporal al terminar.

NUNCA establecer RESTORE_DATABASE_URL igual a DATABASE_URL productiva.
El script contiene una protección adicional que rechaza esa condición.
