IMPACTO NEXORA v1.23.0
DOCUMENTACION TECNICA DE ENTREGA
================================

1. IDENTIDAD DEL SISTEMA
------------------------
Nombre operativo: Impacto Nexora
Empresa: Impacto Media Agency LLC
Arquitectura: aplicación web Flask + SQLAlchemy + MySQL
Repositorio: GitHub
Runtime / aplicación: Railway
Base de datos: MySQL en Railway
Dominio y DNS: Hostinger
Archivos persistentes y backups lógicos: Railway Volume del servicio ImpactoAPP

2. FLUJO DE DESPLIEGUE
----------------------
Código:
GitHub -> Railway

El repositorio main es la fuente de código desplegable.
Antes de desplegar:
1) subir cambios a GitHub;
2) esperar GitHub Actions;
3) desplegar únicamente cuando el workflow termine SUCCESS;
4) validar producción.

Hostinger NO despliega Nexora. Se utiliza únicamente para dominio/DNS.

3. SERVICIOS Y PERSISTENCIA
---------------------------
MySQL utiliza su propio volumen gestionado por el servicio MySQL.
ImpactoAPP utiliza un volumen separado para:
- uploads;
- backups lógicos.

Montaje recomendado/actual:
RAILWAY_VOLUME_MOUNT_PATH=/data

Rutas predeterminadas cuando existe el volumen:
- /data/uploads
- /data/backups

No adjuntar mysql-volume al servicio ImpactoAPP.

5. ARRANQUE
-----------
Dockerfile instala dependencias y cliente MySQL.

Comando de arranque:
python -m scripts.init_db
gunicorn -w 3 -b 0.0.0.0:${PORT:-5000} wsgi:app

scripts.init_db es idempotente para la estructura inicial existente.

6. HEALTHCHECK
--------------
Ruta:
GET /healthz

Respuesta esperada:
200 {"status":"ok"}

El healthcheck realiza SELECT 1 contra la base.
No expone credenciales ni información sensible.

8. BACKUPS
----------
Backups automáticos:
Configuración -> Backups automáticos

Predeterminado:
- diario 02:00;
- retención 14 días;
- máximo 30 archivos.

El sistema utiliza:
- MySQL GET_LOCK para exclusión distribuida;
- lock de filesystem sobre el Volume;
- archivo temporal .part + replace atómico.

Backup manual:
python -m scripts.backup

Validación:
python -m scripts.restore_backup /ruta/backup.zip

Restore real:
RESTORE_DATABASE_URL debe apuntar a una base separada.
El script bloquea restauración cuando el destino coincide con DATABASE_URL.

5) reproducir en ambiente de pruebas;
6) no modificar directamente la base productiva sin backup.
